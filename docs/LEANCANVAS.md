## ① 문제 (Problem)

- 수영, 헬스, 친구 모임 주최자는 메신저 단체방에서 참석 여부를 손으로 세고 입금 내역을 대조한다.
- 응답이 대화에 묻혀 최종 인원 파악이 늦고, 정산 대상과 금액 계산 실수가 반복된다.
- 참가자 다수는 앱 가입을 꺼린다. 가입을 요구하면 응답 자체가 줄어든다.

**기존 대안**: 메신저 단체방 공지 + 수기 집계, 엑셀/메모장 정산, 일반 투표 기능 [가설]

## ② 고객 세그먼트 (Customer Segments)

| 구분 | 설명 |
|---|---|
| 핵심 고객: 주최자 (회원) | 수영/헬스/친구 모임 운영자. 모바일 위주. 매주 회차를 올리고 당일 인원을 확정하며 모임 후 비용을 나눠 받는다 |
| 사용자: 참가자 (회원 또는 비회원) | 메신저로 받은 링크에서 이름만 입력해 응답하고, 정산 링크로 본인 금액과 입금 상태를 확인한다 |

**얼리어답터**: 매주 정기적으로 모이고 회비/비용 정산이 반복되는 소규모 생활체육 모임 [가설]

## ③ 가치 제안 (Unique Value Proposition)

> **모임 주최자가 일정 공지, 참석 확인, 1/N 정산을 링크 하나로 끝낸다.**

- 참가자는 가입 없이 30초 안에 응답한다.
- 주최자는 응답 현황과 입금 현황을 한 화면에서 본다.

**상위 개념(High-level concept)**: 모임용 "참석 확인 + 더치페이" 도구 [가설]

## ④ 해결책 (Solution)

| 문제 | 해결책 | PRD |
|---|---|---|
| 참석 인원을 손으로 센다 | 회차별 초대 링크 + 비회원 RSVP, 응답 현황 실시간 집계 | FR-05, FR-06, FR-07 |
| 응답이 묻혀 인원 파악이 늦다 | 참석/불참/미정/미응답 분류, 정원 초과 강조 표시 | FR-07 |
| 정산 계산과 입금 대조가 번거롭다 | 참석자 기준 1/N 자동 계산(나머지 원은 주최자 부담), 입금 상태 수동 체크, 정산 공유 링크 | FR-08, FR-09, FR-10 |
| 매주 일정을 새로 올리기 번거롭다 | 정기모임(그룹) + 멤버 명부 + 회차 복제 | FR-02, FR-03, FR-04 |
| 가입 장벽 | 토큰 링크 기반 비회원 접근, 이메일/Google 로그인은 주최자 중심 | FR-01 |

**MVP 제외(Phase 2 이후)**: 오픈 모집, 품목별 정산, 알림톡/SMS, PG 결제와 자동 입금 확인, 월 회비 정기 청구, 대기자 명단, 공동 주최자

## ⑤ 경쟁 우위 (Unfair Advantage)

PRD에 명시된 내용이 없어 아래는 모두 **[가설]** 이다. 복제하기 어려운 진짜 우위가 있는지 검증이 필요하다.

- 참가자 가입 불필요 + 링크 하나로 RSVP와 정산을 모두 처리하는 흐름(기능 자체는 복제 가능)
- 반복 모임의 멤버 명부와 회차 기록이 쌓이면 생기는 전환 비용(데이터 락인)
- 모임 주최자 커뮤니티 접점(직접 운영 중인 모임 등) [확인 필요]

## ⑥ 수익 흐름 (Revenue Streams)

PRD는 수익 모델을 정의하지 않았다. Phase 1은 **검증 단계(무료)** 로 두고, 아래는 후보안이다.

| 후보 | 설명 | 비고 |
|---|---|---|
| 프리미엄 구독 | 알림톡 리마인드, 월 회비 정기 청구, 공동 주최자 등 Phase 2 기능을 유료화 | 가장 자연스러운 후보 [가설] |
| 정산 수수료 | PG 결제와 자동 입금 확인 도입 시 결제 건당 수수료 | Phase 3 이후, 결제 규제 검토 필요 |

**결정 필요**: 유료화 시점과 방식. 지금 정하지 않으면 Phase 2 범위 결정이 흔들린다.

## ⑦ 비용 구조 (Cost Structure)

| 구분 | 항목 |
|---|---|
| 고정비 | 개발/디자인 인건비, 도메인 |
| 변동비 | Supabase(DB, Auth) 사용량, 호스팅(Next.js 배포) |
| Phase 2 | 알림톡/SMS 발송 비용(외부 메시징 사업자) |
| Phase 3 | PG 수수료, 결제 규제 대응 비용 |

**비용 특성**: Phase 1은 인프라 비용이 낮고 개발 인건비가 대부분이다. 비회원 접근은 사용자 수에 따라 DB 읽기/쓰기 비용으로 이어진다 [가설].

## ⑧ 주요 지표 (Key Metrics)

| 구분 | 지표 | 목표 | 측정 |
|---|---|---|---|
| North Star | 월간 정산 완료 회차 수 | - | `settlements` 완료 상태 건수의 월 집계 |
| 보조 | 비회원 RSVP 응답률 (응답 수 / 링크 열람 수) | 70% 이상 (가정) | 링크 열람 이벤트 대비 RSVP 생성 수 |
| 보조 | 회차 생성 후 24시간 내 응답률 (명부 대비) | 60% 이상 (가정) | 회차 생성 시각과 응답 시각 차이 |
| 보조 | 주최자 4주 재방문율 (회차 3건 이상 생성 주최자 비율) | - | 주최자별 회차 생성 수 |

**목표(Phase 1)**: 회차 5분 이내 등록(G1), 비회원 RSVP 30초 이내(G2), 참석자 기준 1/N 자동 정산(G3)

## ⑨ 채널 (Channels)

| 채널 | 역할 |
|---|---|
| 메신저 링크 공유 | 핵심 채널. 주최자가 단체방에 초대/정산 링크를 붙여넣어 참가자가 유입된다. 공유 문구 복사 기능 제공(FR-14) |
| 웹앱(모바일 우선) | 주최자의 모임/회차/정산 관리 (360px 기준, 다크모드 지원) |
| 참가자 → 주최자 전환 | 초대/정산 페이지에서 선택적 로그인/가입 안내로 새 주최자를 확보 [가설] |

PRD의 Q8 결정에 따라 알림 없이 응답을 독려하는 방법은 Phase 1에서 **메신저 공유 문구 복사** 만 제공한다.

## 핵심 리스크와 검증 과제

| 가정 | 위험 | 검증 방법 |
|---|---|---|
| 주최자는 기존 메신저 방식보다 링크 하나를 선호한다 | 기존 습관(단체방 + 수기 집계)이 충분히 편해서 전환하지 않음 | 실제 모임 3~5곳에서 2~4주 시범 운영 [가설] |
| 참가자는 로그인 없이 링크로 응답한다 | 링크 유출, 스팸, 위조 응답(R1, R2) | 토큰 재발급, 속도 제한, 주최자 응답 삭제 |
| 수동 입금 체크만으로 정산 부담이 충분히 준다 | 주최자의 수동 작업이 여전히 큼 | 정산 완료 회차 수와 자가 입금 표시(FR-12) 사용률 확인 |
| 무료로 시작해도 이후 유료 전환이 가능하다 | 수익 모델 부재 | Phase 2 착수 전에 지불 의사 인터뷰 [가설] |
