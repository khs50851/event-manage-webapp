## 한눈에 보기

| Phase | 목표 | 핵심 산출물 | 상태 |
|---|---|---|---|
| Phase 1 (MVP) | 주최자가 모임·회차를 만들고, 비회원이 링크로 RSVP하고, 1/N 정산을 수동 입금 확인까지 마친다. **UI(더미 데이터) → Supabase 연동 순서로 진행** | FR-01~FR-14 | 진행 중 (UI 단계 완료·U5-7 검토 게이트 승인, U3-1 로그인 유지 회귀 확인 1건 남음(I2-6에서 함께 확인), 연동 단계 I0 완료(2026-10-12), I1 대기) |
| Phase 2 | 응답 독려 자동화와 정산·모집 기능 확장 | 알림톡, 오픈 모집, 품목별 정산, 월 회비, 대기자, 공동 주최자 | 대기 |
| Phase 3 | 결제 자동화 | PG 결제, 자동 입금 확인, 환불, 통계 | 대기 |

## 현재 상태 (출발점)

- Next.js 16 + Supabase Auth 스타터 킷, 개발 도구(ESLint, Prettier, Husky, commitlint, CI) 설정 완료.
- 이벤트 도메인 테이블 없음. 기존 `accounts`/`quotes`/`quote_items`/`instruments`는 무관하며 수정하지 않는다(Q7: `accounts` 미사용, 신규 `profiles` 테이블 사용 — PRD v0.6). 이 항목은 출발점 기준이며 I0 완료 후 현황은 `docs/guides/db-schema.md`와 CLAUDE.md를 따른다.
- `list_migrations`가 비어 있으므로 이후 모든 DDL은 `apply_migration`으로 적용한다.
- `lib/supabase/database.types.ts`가 없다. 스키마 적용 후 `generate_typescript_types`로 생성한다.
- 테스트 프레임워크 없음. 검증은 `check-all`, `build`, playwright 수동 검증으로 한다.
- **DB·Supabase 연동은 UI 완성 이후**로 미룬다. 그 전까지 이벤트 도메인 화면은 더미 데이터로 구현한다.

## Phase 1: MVP

**진행 방식: UI 먼저, 연동은 나중.** 데이터베이스와 Supabase 연동은 UI 구성이 끝난 뒤에 진행한다. UI 단계에서는 더미 데이터로 화면과 흐름을 완성하고, 화면 검토를 마친 뒤 연동 단계에서 더미를 실제 데이터로 교체한다.

### 마일스톤 의존 관계

```
[UI 단계: 더미 데이터]
U0 UI 기반 ─▶ U1 인증 UI ─▶ U2 모임·멤버·회차 ─▶ U3 초대·RSVP ─▶ U4 정산 ─▶ U5 대시보드·UI 검토
                                                                                    │
                                                                         (UI 검토 통과 = 게이트)
                                                                                    ▼
[연동 단계: Supabase]
I0 스키마·RLS ─▶ I1 데이터 계층 교체 ─▶ I2 인증 연동(Google) ─▶ I3 RSVP·토큰 연동 ─▶ I4 정산 연동 ─▶ I5 출시 점검
```

### UI 단계 원칙

- 더미 데이터는 `lib/mock/`에 모아 두고, 화면은 `lib/data/`의 조회 함수만 호출한다. 연동 단계에서는 이 함수의 구현만 Supabase 호출로 바꾸고 화면 코드는 건드리지 않는다.
- 도메인 타입은 PRD 6장 엔티티 기준으로 수동 정의한다. 연동 단계에서 `generate_typescript_types` 결과로 대체한다.
- 쓰기 동작(저장, 삭제, 토글)은 화면 내 상태로만 시뮬레이션하고 새로고침하면 초기화된다. 실제 저장은 하지 않는다.
- 더미 데이터에는 빈 상태, 정원 초과, 마감, 취소, 만료 토큰 같은 경계 사례를 반드시 포함한다. PRD 7장의 로딩/빈/오류 상태를 모두 화면으로 만든다.
- 로딩 상태 확인을 위해 더미 조회에 인위적인 지연을 줄 수 있다. 요청별 데이터 화면은 `<Suspense>` + 스켈레톤을 지금부터 적용해 구조를 맞춘다.
- DB 마이그레이션, RLS, Supabase 클라이언트의 이벤트 데이터 호출은 UI 단계에서 하지 않는다. 기존 Supabase Auth 로그인 자체는 이미 동작하므로 `/protected/*` 화면 확인에 그대로 쓴다.

### UI 단계

| I3-7 | 주최자 현황 | 응답 현황 실데이터 조회, 대리 입력·삭제 저장 | U3-7, U3-8 화면 실데이터 동작 |
| I3-8 | 반영 시간 | 제출 후 주최자 화면 반영 3초 이내 | 측정 확인 |

#### I4. 정산 연동 (FR-08, FR-09, FR-10, FR-12, FR-14)

| ID | 작업 | 내용 | 완료 기준 |
|---|---|---|---|
| I4-1 | 정산 저장 | 정산·정산 항목 저장(U4-1 계산 함수 재사용), 금액 원 단위 정수 | 저장값이 화면 계산과 일치 |
| I4-2 | 정산 토큰 | 초대 토큰과 별개의 값으로 발급·재발급 | 두 토큰이 서로의 권한을 대신하지 못함 |
| I4-3 | 정산 조회 | `/s/[token]` 실데이터 조회, 타인 금액·상태·연락처 메모 미노출. `app/actions/settlements.ts`의 본인 상태 조회 액션을 실데이터로 교체하고, shareId를 바꿔 가며 같은 정산의 타인 상태를 조회하지 못하도록 속도 제한·본인 확인 수단 검토 | 무효·만료 안내 확인, 타인 항목 조회 불가 |

| I4-6 | 변경 재계산 | 총액·대상 변경 시 재계산 저장, 완료 항목 상태 유지 | 경고 후 재계산 확인 |
