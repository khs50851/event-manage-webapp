# PRD: 이벤트 관리 웹앱 MVP (정기모임 · RSVP · 균등분담 정산)

- 상태: 초안 v0.3 (2026-10-08) — v0.2: Google 로그인/가입 추가 / v0.3: 오픈 질문 Q1~Q11 결정 반영(정원 초과 허용, 응답 현황 전체 공개)
- 슬러그: `event-management-mvp`
- 표기: "가정"은 요청자 확인 없이 정한 기본값이다. 9장 질문 Q1~Q11은 2026-10-08 모두 결정되었다.

## 1. 개요

**가치제안**: 모임 주최자가 일정 공지, 참석 확인, 1/N 정산을 링크 하나로 끝낸다.

**배경/문제**
- 수영, 헬스, 친구 모임 주최자는 메신저 단체방에서 참석 여부를 손으로 세고 입금 내역을 대조한다.
- 응답이 대화에 묻혀 최종 인원 파악이 늦고, 정산 대상·금액 계산 실수가 반복된다.
- 참가자 다수는 앱 가입을 꺼린다. 가입 없이 링크로 응답할 수 있어야 한다.

**목표 (Phase 1)**
- G1. 주최자가 정기모임(그룹)을 만들고 회차(이벤트)를 5분 이내에 등록한다.
- G2. 비회원 참가자가 초대 링크에서 로그인 없이 30초 이내에 RSVP를 제출한다.
- G3. 회차 종료 후 참석자 기준 1/N 정산을 자동 계산하고, 주최자가 입금 여부를 수동 체크한다.

**비목표**
- 오픈 모집(공개 탐색·신청), 품목별 정산, 알림톡/SMS 발송, PG 결제·자동 입금 확인, 월 회비 정기 청구는 Phase 2 이후다(10장, 4장 Won't).

## 2. 대상 사용자

| 페르소나 | 설명 | 핵심 상황 |
|---|---|---|
| 주최자 (회원) | 수영/헬스/친구 모임 운영자. 모바일에서 주로 사용 | 매주 회차를 올리고, 당일 인원을 확정하고, 모임 후 비용을 나눠 받는다 |
| 참가자 (회원 또는 비회원) | 모임 멤버 또는 1회성 이벤트 초대 대상 | 메신저로 받은 링크를 눌러 이름만 입력하고 참석/불참을 답한다. 정산 링크로 본인 금액과 입금 상태를 확인한다 |

가정: 주최자는 이메일 또는 Google 계정(Supabase Auth)으로 가입한 회원이다. 참가자의 로그인은 선택이다. 공동 주최자(복수 관리자)는 MVP에서 지원하지 않는다.

## 3. 사용자 시나리오

**S1. 정기모임 운영 (주최자)**
1. 로그인 후 모임 "화요 수영반"을 만든다.
2. 모임에 멤버 이름 목록을 등록한다(비회원 포함, 이름만 필수).
3. 이번 주 회차(일시, 장소, 정원, 예상 비용 메모)를 등록한다.
4. 모임 공용 초대 링크 또는 회차 링크를 메신저에 공유한다.
5. 응답 현황(참석/불참/미정/미응답)을 실시간으로 확인한다.

**S2. 1회성 이벤트 (주최자)**
- 멤버 없는 이벤트를 바로 만든다. 내부적으로는 S1과 같은 구조(멤버 0명인 모임 1개 + 회차 1개)를 쓴다.

**S3. 비회원 RSVP (참가자)**
- 링크를 열면 회차 정보가 보이고, 이름 입력 후 참석/불참/미정을 고른다. 같은 기기에서 다시 열면 이전 응답을 수정할 수 있다.

**S4. 정산 (주최자, 참가자)**
- 회차 종료 후 주최자가 총 비용과 입금 계좌 안내 문구를 입력한다. 시스템이 참석자 수로 1/N을 계산한다.
- 주최자가 정산 링크를 공유한다. 참가자는 본인 금액과 계좌 안내를 확인하고 입금한다.
- 주최자가 입금 확인 후 참가자별로 "입금 완료"를 체크한다.

## 5. 비기능 요구사항

**성능**
- RSVP 제출 후 주최자 화면 반영 3초 이내(새로고침 또는 폴링 허용, 가정).
- 초대/정산 링크 페이지 LCP 2.5초 이내(4G 환경, 가정).
- 한 모임당 회차 500건, 회차당 응답 200건까지 목록 응답 지연 없이 지원(가정).

**보안**
- 모든 신규 테이블은 RLS 활성화. 정책은 `(select auth.uid())` 형태로 작성한다. 클라이언트 권한 체크는 UX 보조일 뿐이며 접근 제어는 DB 레벨로 강제한다.
- 비회원 접근은 토큰 기반이다. 토큰은 해당 회차(초대) 또는 정산 단위로만 유효하며, 다른 모임·회차의 데이터는 어떤 경우에도 조회할 수 없어야 한다.
- 토큰은 목록 조회로 열거할 수 없어야 한다(익명 역할에 테이블 전체 SELECT 금지). 비회원 쓰기는 "토큰 검증 후 단일 회차의 RSVP 생성/수정"만 허용한다.
- Google OAuth는 Supabase Auth의 PKCE 흐름을 사용하고, 콜백은 `/auth/*` 접두사 아래(예: `/auth/callback`)에 두어 `proxy.ts` 허용 경로를 재사용한다. 클라이언트 시크릿은 Supabase 대시보드에만 두고 저장소·번들에 넣지 않는다.
- `service_role` 키를 클라이언트 번들에 두지 않는다. 비회원 경로의 서버 처리 방식은 설계 단계에서 결정한다.
- 비회원 입력(이름, 메모)은 길이 제한(이름 30자)과 출력 이스케이프를 적용한다.
- 개인정보 최소 수집: 비회원은 이름만 필수, 연락처는 수집하지 않는다(가정).

**`proxy.ts` 허용 경로 영향**
- 현재 `updateSession()`은 `/`, `/login*`, `/auth*` 외 미인증 요청을 `/auth/login`으로 보낸다. 비회원 경로(초대 `/i/[token]`, 정산 `/s/[token]`)는 허용 목록에 추가해야 한다. 허용은 해당 두 접두사로 한정하고, `/protected/*`는 계속 차단한다.
- 위 변경은 `lib/supabase/proxy.ts`의 쿠키 동기화 순서 경고를 지켜야 한다. 허용 경로에서도 세션 갱신은 유지한다.

**렌더링 제약 (`cacheComponents`)**
- 토큰·쿠키·세션에 따라 달라지는 데이터 화면(초대 페이지, 정산 페이지, 대시보드, 응답 현황)은 `<Suspense>`로 감싸 스트리밍하고 로딩 스켈레톤을 제공한다.
- `params`는 Promise이므로 await 한다. 토큰 페이지는 정적 캐시 대상이 아니다.

**접근성**
- WCAG 2.1 AA 수준 색 대비, 폼 라벨 연결, 키보드만으로 RSVP 제출 가능.
- 응답 상태는 색상만이 아니라 텍스트로도 구분한다.

**모바일 우선**
- 360px 너비 기준 설계. 터치 대상 최소 44x44px. 초대/정산 페이지는 한 화면 스크롤 내 핵심 동작(응답 버튼)이 보여야 한다.
- 다크모드는 기존 디자인 토큰을 따른다.

**데이터 마이그레이션**
- 모든 DDL은 `apply_migration`으로 적용하고, 적용 직후 보안·성능 advisors를 확인한다. 기존 `accounts`/`quotes`/`quote_items`/`instruments`는 수정하지 않는다.

## 6. 데이터 요구사항

현황 조사(2026-10-08, `list_tables`): `public.instruments`, `accounts`, `quotes`, `quote_items`만 존재하며 모두 이벤트 도메인과 무관하다. 이벤트 관련 테이블은 신규 생성이 필요하다. 아래는 DDL이 아닌 초안이다. 이름 충돌을 피하려 기존 `accounts`는 주최자 프로필로 재사용하지 않는다(가정: Notion 연동 정보를 포함하는 별개 용도, 결정 Q7: 신규 프로필).

### 엔티티와 관계 (초안)

| 엔티티 | 핵심 속성 | 관계 |
|---|---|---|
| `groups` (모임) | 이름, 설명, 소유자(auth 사용자) | 1:N members, 1:N events |
| `group_members` (멤버 명부) | 이름, 메모, 소속 모임 | N:1 groups |
| `events` (회차) | 제목, 시작 시각, 장소, 정원, 응답 마감, 상태(예정/취소/종료), 초대 토큰 | N:1 groups, 1:N rsvps, 1:1 settlements |
| `rsvps` (응답) | 표시 이름 스냅샷, 응답값(참석/불참/미정), 출처(본인/주최자), 멤버 연결(선택), 비회원 식별자 | N:1 events, N:1 group_members(선택) |

제약 요구
- 응답 이름과 정산 항목은 이름 스냅샷을 가져 멤버 삭제 후에도 기록이 유지된다.
- 한 회차에서 한 비회원 식별자는 응답 1건만 가진다.
- 금액은 원 단위 정수로 저장한다(소수 없음).
- 소유자 컬럼은 모든 하위 엔티티가 상위 모임을 통해 판별할 수 있어야 한다.

## 8. 성공 지표

**North Star**: 월간 "정산 완료 회차 수"(모든 대상이 입금 완료로 확정된 회차). 측정: `settlements` 상태가 완료로 바뀐 건수를 월 단위 집계.

**보조 지표**
- 비회원 RSVP 응답률 = 응답 수 / 초대 링크 열람 수. 목표 70% 이상(가정). 측정: 링크 열람 이벤트와 RSVP 생성 수 비교.
- 회차 생성 후 24시간 내 응답률(명부 대비) 60% 이상(가정). 측정: 회차 생성 시각과 응답 시각 차이.
- 주최자 4주 재방문율: 회차 3건 이상 생성한 주최자 비율. 측정: 주최자별 회차 생성 수.
